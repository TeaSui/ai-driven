# Runbook 05: Deploy and Rollback

## Overview

The AI-Driven API uses **CodeDeploy blue/green deployment** on ECS Fargate.
Traffic shifts all-at-once from the blue (original) task set to the green (replacement) task set.
On failure or alarm trigger, CodeDeploy automatically rolls back to blue.

**AppSpec location:** `appspec/appspec.json`
**Task definition template:** `appspec/taskdef.json`

---

## Architecture

```
Internet → ALB:80 (prod listener) → Blue TG → Blue ECS tasks
                                 ↑ switches after deployment
ALB:8080 (test listener) → Green TG → Green ECS tasks (pre-production validation)
```

CodeDeploy stages:
1. Start replacement (green) task set.
2. Run health checks on test listener (port 8080).
3. Reroute production listener to green.
4. Wait 5 minutes, then terminate blue task set.

---

## Pre-Deploy Checklist

- [ ] All CI tests pass on the branch being deployed.
- [ ] Database migrations have been applied and are **backward-compatible** with the current running version. The blue (current) and green (new) task sets run simultaneously during cutover — schema changes must not break the old code.
- [ ] Docker image has been built and pushed to ECR (CI does this automatically; for manual deploys the script handles it).
- [ ] `appspec/taskdef.json` reflects the latest ECS task definition (generated by `cdk synth` or CI).
- [ ] `appspec/appspec.json` is present and valid.
- [ ] Confirm the target stage: `dev`, `staging`, or `prod`.
- [ ] For `prod`: confirm change window with the team.

## Deploy Command

```bash
# Set environment
export AWS_PROFILE=ai-driven
export AWS_REGION=ap-southeast-1
export STAGE=prod           # dev | staging | prod

# Deploy a specific image tag (e.g. git commit SHA or semantic version)
./scripts/deploy.sh <image-tag>

# Example
./scripts/deploy.sh 1.4.2
./scripts/deploy.sh a3f9c21
```

The script will:
1. Build and push the Docker image to ECR (skippable if image is already pushed — set `SKIP_BUILD=1`).
2. Register a new ECS task definition revision with the new image URI.
3. Create a CodeDeploy deployment.
4. Poll and print deployment status every 15 seconds.
5. Exit 0 on success, exit 1 on failure with an error summary.

### Environment variable reference

| Variable | Default | Description |
|---|---|---|
| `AWS_PROFILE` | `ai-driven` | AWS credentials profile |
| `AWS_REGION` | `ap-southeast-1` | Target region |
| `STAGE` | `dev` | Deployment stage |
| `ECR_ACCOUNT_ID` | auto-detected | AWS account ID for ECR |
| `POLL_INTERVAL` | `15` | Seconds between status polls |
| `DEPLOY_TIMEOUT` | `600` | Max wait seconds before timeout |

## Monitoring During Deploy

### CloudWatch console (recommended during prod deploys)

1. Open the [CodeDeploy deployment console](https://ap-southeast-1.console.aws.amazon.com/codesuite/codedeploy/deployments).
2. Click the active deployment ID.
3. Watch the **Deployment lifecycle events** panel for each stage.

### ALB 5xx alarm

The CloudWatch alarm `<stage>-api-5xx-errors` triggers automatic rollback if the ALB returns 10 or more 5xx responses in a 1-minute window, evaluated over 2 periods.

Monitor it here (replace `dev` with your stage):
```
CloudWatch → Alarms → dev-api-5xx-errors
```

### Live traffic health check

```bash
# Replace with your ALB DNS name from CDK output
ALB_DNS=$(aws cloudformation describe-stacks \
  --stack-name "ai-driven-${STAGE}-deployment" \
  --query "Stacks[0].Outputs[?OutputKey=='AlbDnsName'].OutputValue" \
  --output text)

# Production endpoint
curl -sf "http://${ALB_DNS}/health" | jq .

# Test (green) endpoint — available during deployment only
curl -sf "http://${ALB_DNS}:8080/health" | jq .
```

### ECS task status

```bash
CLUSTER=$(aws cloudformation describe-stacks \
  --stack-name "ai-driven-${STAGE}-compute" \
  --query "Stacks[0].Outputs[?OutputKey=='ClusterArn'].OutputValue" \
  --output text)

aws ecs list-tasks --cluster "${CLUSTER}" --family "${STAGE}-api"
```

## Rollback Procedure

### Automatic rollback

CodeDeploy automatically rolls back when:
- The deployment itself fails (health check failure, task launch failure).
- The `<stage>-api-5xx-errors` CloudWatch alarm fires during deployment.

No action required — CodeDeploy restores the prod listener to the blue target group.

### Manual rollback

If you need to stop an in-progress deployment or roll back a completed (but bad) deployment:

```bash
export AWS_PROFILE=ai-driven
export AWS_REGION=ap-southeast-1
export STAGE=prod

# Automatic: finds and stops the in-progress deployment, then polls until done
./scripts/rollback.sh

# Explicit: stop a specific deployment
./scripts/rollback.sh d-XXXXXXXXX
```

The rollback script will:
1. If a deployment is in-progress: stop it with `--auto-rollback-enabled`.
2. If no deployment is in-progress: re-deploy the previous successful revision.
3. Poll until the rollback deployment succeeds.

### Emergency: direct target group switch (last resort)

If CodeDeploy is unavailable, you can manually reroute the ALB listener:

```bash
# Get the blue TG ARN from CDK outputs
BLUE_TG_ARN=$(aws cloudformation describe-stacks \
  --stack-name "ai-driven-${STAGE}-deployment" \
  --query "Stacks[0].Outputs[?OutputKey=='BlueTgArn'].OutputValue" \
  --output text)

# Get the prod listener ARN
LISTENER_ARN=$(aws elbv2 describe-listeners \
  --load-balancer-arn "$(aws elbv2 describe-load-balancers \
    --names "${STAGE}-api-alb" \
    --query 'LoadBalancers[0].LoadBalancerArn' --output text)" \
  --query "Listeners[?Port==\`80\`].ListenerArn" \
  --output text)

# Switch prod listener back to blue
aws elbv2 modify-listener \
  --listener-arn "${LISTENER_ARN}" \
  --default-actions Type=forward,TargetGroupArn="${BLUE_TG_ARN}"
```

Note: do this only in a genuine emergency. It bypasses CodeDeploy state tracking and will cause the next CodeDeploy deployment to behave unexpectedly until you reset the deployment group state.

## Post-Deploy Verification

```bash
# 1. Confirm /health returns 200 and correct version
curl -sf "http://${ALB_DNS}/health" | jq .

# 2. Confirm no errors in the last 5 minutes
aws cloudwatch get-metric-statistics \
  --namespace AWS/ApplicationELB \
  --metric-name HTTPCode_ELB_5XX_Count \
  --dimensions "Name=LoadBalancer,Value=$(aws elbv2 describe-load-balancers \
    --names "${STAGE}-api-alb" \
    --query 'LoadBalancers[0].LoadBalancerArn' --output text | cut -d/ -f2-)" \
  --start-time "$(date -u -d '5 minutes ago' +%Y-%m-%dT%H:%M:%SZ 2>/dev/null || date -u -v-5M +%Y-%m-%dT%H:%M:%SZ)" \
  --end-time "$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
  --period 300 \
  --statistics Sum

# 3. Confirm ECS tasks are healthy
aws ecs describe-services \
  --cluster "${CLUSTER}" \
  --services "${STAGE}-api" \
  --query 'services[0].{running:runningCount,desired:desiredCount,pending:pendingCount}'

# 4. Confirm the deployment succeeded in CodeDeploy
aws deploy list-deployments \
  --application-name "${STAGE}-api" \
  --deployment-group-name "${STAGE}-api-bg" \
  --include-only-statuses Succeeded \
  --query 'deployments[0]' \
  --output text
```

## Troubleshooting

| Symptom | Likely cause | Action |
|---|---|---|
| Green tasks fail health check | `/health` endpoint broken in new image | Check ECS task logs in CloudWatch, rollback |
| Deployment stuck in `InProgress` > 30 min | Task failing to start (OOM, bad env var) | Check ECS task stopped reason, rollback |
| Rollback script says "no in-progress deployment" | Deployment already completed | Manually re-deploy previous tag via `deploy.sh` |
| `5xx-errors` alarm fires post-deploy | New code has runtime errors | Check CloudWatch Logs `/ecs/api`, rollback |
| CodeDeploy says "revision not found" | `appspec.json` or task def missing/malformed | Validate JSON, re-render, retry |

### Viewing ECS task logs

```bash
# List log streams for the api container (adjust log group name if changed)
aws logs describe-log-streams \
  --log-group-name /ecs/api \
  --order-by LastEventTime \
  --descending \
  --max-items 5

# Tail a specific stream
aws logs get-log-events \
  --log-group-name /ecs/api \
  --log-stream-name <stream-name> \
  --start-from-head \
  --limit 100
```

## Database Migration Policy

Run migrations **before** deploying new code. Migrations must be backward-compatible:
- Do not drop columns — add new ones and deprecate old ones gradually.
- Do not rename columns in a single deployment — use a two-phase approach (add new, migrate data, remove old).
- Do not change column types in a way that breaks the current running version.

Migration command:
```bash
AWS_PROFILE=ai-driven STAGE=prod poetry run alembic upgrade head
```

Verify migration completed before running `deploy.sh`.
